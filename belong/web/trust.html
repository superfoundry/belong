Your hidden details can improve a match, but they are never shown: not to other people, and not to Belong. This page shows how it works, and gives you and your agent the tools to test it yourselves.

Prototype

Every check on this page really runs. But private matching doesn't yet run inside secure hardware, so today you still have to trust the machine it runs on. The tables below separate what you can verify now from what arrives with the hardware enclave in step 3.

Mock

This version's Matchmaker AI is a mock. When it's on, a model reached over OpenAI's API judges whether two listings suit each other, standing in for the model that will run inside secure hardware. It's used only with synthetic and test profiles. It's given only what people show and their descriptions, never a hidden detail, a first name or an id: the Warden agent checks every request before it goes, and an independent audit checks it again. Every check on this page runs as if it were enclosed: the rules still decide everything hard and exact, its answer can only be a verdict and a number, and the Warden agent checks every match the same way.

How it's built

Two agents, deliberately split

The Matchmaker agent finds matches. The Warden agent checks everything that goes into private matching and everything that comes out. Both are open source for anyone to read, and the Warden agent still treats the Matchmaker agent as hostile: whatever the Matchmaker agent hands over, the Warden agent checks before it goes, and that includes every request to the mock Matchmaker AI. One gap stays while the AI is a mock: the code that carries those requests to the model is Matchmaker code, trusted to send only what the Warden agent passed, until the model runs enclosed with it.

Why you don't need to trust the Matchmaker agent

You can read how it matches, but you don't have to rely on it. It can only hand the Warden agent a proposal: two ids, yes-or-no flags, scores and field names. There's no free text, so there's nowhere to hide a hidden detail. The Warden agent then writes the introduction itself from shown details only, and checks it for hidden values. Privacy rests on the Warden agent, and its code never depends on the Matchmaker's. The Matchmaker AI is held the same way: it judges only pairs the rules allow, it's given only shown details and descriptions, and its answer is read as a verdict and a number, nothing more.

What "not even us" requires

Open code isn't enough on its own. You also need proof that the open code is what is running, and that nobody can reach inside private matching, not even the people who run Belong. That's the job of the hardware enclave: see the roadmap.

Verify in your browser

These checks run on your computer

They use your browser's own cryptography, so they don't take our word for anything.

Check 1

The code you can read is the code that was measured

Downloads every open-source file of both agents, hashes it with SHA-256 in your browser, and compares the results with the Warden agent's and the Matchmaker agent's measurements in the attestation document.

Check 2

The attestation document

You pick a random nonce; Belong answers with its measurements and rules. In production the enclave hardware signs this document, so it can't be faked or replayed.

Check 3

Nobody has deleted or edited a receipt

Every check the Warden agent runs writes a receipt: the check, the result, the time and a hash, never content. Each receipt's hash covers the one before it, so removing or changing any receipt breaks the chain from that point on. Whoever runs the server could still replace the whole log with a recomputed one, or cut off its end: checkpoints held by someone else, which would stop that, are production work.

Test with your agent

Try to make it leak

These run in a sandbox: the same Warden and Matchmaker agents, with 300 synthetic people. Nothing touches real listings.

Canary test

Plant secrets, then look for them everywhere

Creates people with unique secret words in their hidden details and private descriptions, runs a full week of matching (questions, introductions, yes and no, comparing details), then searches what was sent out: each canary's own random words in every byte, and anything else it hides in whatever was sent about it to someone else, as whole words, apart from what that person may see anyway. The canaries never agree to compare anything, so any hit at all is a leak.

Attack suite

Try to break in and get details out

Tries every attack in the suite: identifying intents, forged and mislabelled listings, a compromised Matchmaker agent, a hostile or obedient Matchmaker AI, forged outputs, and comparing details without consent. Each must be blocked, and the result names the rule that stopped it.

API for agents

Your agent can run all of this

Everything above is available over plain HTTP. A certified agent can run these before it trusts Belong with your details, and again whenever it likes.

CallWhat it gives you
GET /api/trust/attestation?nonce=…Measurements of both agents, plus the rules in force
GET /api/trust/sourceEvery open-source file and its SHA-256
GET /api/trust/source/<file>The file itself, for any file of either agent
GET /api/trust/receipts?from=NThe public receipt log, plus the previous hash so you can verify from any point
POST /api/probe/canaryThe canary test; bring your own listings and secrets, and add "matchmaker": "hostile" to run its week with a stand-in Matchmaker AI that says yes to every pair, searching what it was sent too
POST /api/probe/attacksThe attack suite; bring your own intents
