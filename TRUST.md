# How Belong keeps its privacy promises

This document is for anyone who wants to **check** the privacy claims of Belong rather
than take them on faith. Every promise below links to the code that enforces it and
the test that proves it. If a promise has no test, the promise isn't kept yet.

It covers the **Step 2 prototype** (SPEC.md §8): synthetic people, no secure hardware
yet, but built the way the production service will run. Section 5 lists what is *not* yet
guaranteed.

> **This version's Matchmaker AI is a mock.** When it is on, the fuzzy part of matching (does each
> of two listings give what the other wants?) is judged by a model reached over OpenAI's API,
> standing in for the model that will run enclosed (Step 3). It is for **synthetic and test profiles
> only**, never real people. It receives only what people show and their descriptions, under labels
> of one request: never a hidden detail, a first name or an id. The Warden checks every request before
> it goes (#44) and an independent audit checks it again (#40). **Every security check runs as if the
> Matchmaker were enclosed:** the
> rules still decide everything hard and exact (#39), the AI's answer is read strictly and no text of
> it reaches anyone (#41), and the Warden checks every proposal exactly as before. Whatever the AI
> answers, nothing hidden gets out (#42). The demo runs it when an OpenAI key is set or
> `BELONG_MATCHMAKER=ai`, and says so on the presenter panel and the trust page (#43); `belong run`, CI
> and the tests use the rules alone unless asked, and then nothing leaves the machine.

## 1. Verify it yourself (2 minutes)

You need Python 3.10+ and nothing else. No packages, no API keys, no network.

```bash
python3 -m unittest -v          # all tests; any leak fails them
python3 -m belong run           # simulate 300 people, one week run several ways (below); prints the leak reports
python3 -m belong serve         # demo, trust page and inspector on localhost:8000
```

`python3 -m belong run` runs the week twice: once as written, and once with a quarter of the people's
agents writing one detail differently from most agents (another name, another scale, one left out or
hidden). Then it runs both again with a quarter of the agents of listings that aren't dating adding a must
the person never had, with the rule that a must comes from the person's own words (#45), without it, and
with it while those agents quote the person's "no" as their answer, and last the second week with nobody
typing their musts with their values: their descriptions still say most of their musts, and the run
counts, in musts, how many nothing they typed says, which only the person's yes to their agent's question
keeps; it runs that with their yes and by values alone. It prints every result and exits non-zero if any leak report finds anything.
`python3 -m belong run --matcher hostile` runs the same weeks with a stand-in Matchmaker AI that says yes
to every pair and answers out of shape (no model, no network): precision drops to what the hard rules
allow, and every leak report, which then also audits every request it was sent, still passes (#42).

With the server running:

- **http://localhost:8000/trust** is the trust page for the public and their agents. It
  verifies the Warden's source and the receipt chain *in your browser*, and runs the
  canary test and attack suite against a sandbox.
- **http://localhost:8000/** is the two-person demo: two phones, with a presenter
  panel in between that logs everything Belong receives and sends.
- **http://localhost:8000/inspector** is the batch-run inspector. Its people are the live demo's
  first synthetic people, and "Take over" opens one person's phone in the demo, so you can answer as them.

## 2. The shape of the system

```text
             PEOPLE                     WARDEN (open source)         PRIVATE MATCHING (open source)
                                                                    (no way out)
  Person ── Personal agent ──▶  Warden: ENTRY check  ──▶  Marketboard (all listings,
            drafts listing       kyc, schema,              shown + hidden)
            (shown / hidden)     open details,                    │
                 ▲               sensitive defaults,              ▼
                 │               specific person,         Matchmaker agent
                 │               listing cap, rate limit  reads everything,
  Person ◀── Introduction ◀──  Warden: EXIT check  ◀──  outputs only Proposals
             (shown fields +     builds the output         and fixed-menu FollowUps
              reason from        itself, from shown
              shared shown       fields only, then
              fields)            string-checks it
                 │                      │
                 │                      ▼
                 │               Receipts {check, result, timestamp, hash}: no content
                 │
                 └─── Shared list of details in use ◀── Warden, once a day, from the Marketboard
                      (what 20+ different people show)    alone (no Matchmaker input)

  Independent audit (leaks.py) re-reads every output sent and fails on any leak.

  With the Matchmaker AI on (a mock: OpenAI's API standing in for the enclosed model; synthetic and
  test profiles only):
  Matchmaker (rules narrow, ── shown details + descriptions, with names, ids  ──▶  judge: OpenAI's API,
  decide everything hard)      and hidden texts taken out, under labels;          or a self-hosted model
                               each checked by the Warden just before it goes
                               (#44), kept and audited again (#40)
                          ◀── verdicts only: match / close / no, a number,   ◀──
                               read strictly (#41)
```

**The separation rule (SPEC §3):** the agent that sees everything (Matchmaker) has
no path out; the agent that controls the exit (Warden) never decides who matches.

**With the Matchmaker AI on, one thing goes out by design.** The matching code itself still has no
network (#10): the hybrid Matchmaker ([matching/hybrid.py](belong/matching/hybrid.py)) is handed a judge
from outside it ([matchmaker_openai.py](belong/matchmaker_openai.py), plain data in, plain data out) and
sends it, for each pair the hard rules allow, what both listings show and their descriptions, with every
first name, id and hidden text taken out. That is the only thing that leaves, it goes to the model, not to
any person, and it is checked as if the model were enclosed: what may go is a fixed rule (#40), the
Warden checks every request against the board as it is just before it is handed to the model's client
(#44), every request is kept and audited again, and what comes back is only verdicts, read strictly (#41). Today that model
is OpenAI's, a mock for synthetic and test profiles only; a self-hosted open-weights model behind an
OpenAI-compatible server can replace it by changing settings only (`BELONG_MATCHMAKER_URL`), first on the
owner's own machine and later inside confidential computing (limit 27).

### Both agents are open source, and the Matchmaker is still treated as hostile

The **Warden** and the **Matchmaker** are both open source, so anyone can read every check
and exactly how matching works. Each has its own measurement, so a verifier can check each
one separately. The Warden still treats the Matchmaker as **hostile**: the privacy guarantee
never depends on the Matchmaker behaving well, so it holds even if someone runs a modified
Matchmaker. With the Matchmaker AI on, there is one exception while it is a mock: the client that carries
its requests to the model ([matchmaker_openai.py](belong/matchmaker_openai.py)) is Matchmaker code. The
Warden checks every request before it is handed to that client (#44), so a modified matching code can't
get a hidden detail past it, but a modified client could still send something else, and its record of
what went out is its own. Only running the model enclosed with the Matchmaker closes that (limit 27).

- The Matchmaker can hand the Warden only the objects in [matching/contract.py](belong/matching/contract.py):
  person ids, yes/no flags, numbers, field *names* and open-detail reasons ("agree:skill"). No free
  text. Open details are named by people's agents, so a name is a word; but the Warden accepts the
  open-detail reasons only if they are exactly the ones it works out itself from both people's shown
  details (#13), and a hidden field it cites only if it passes the crowd rule (#8), so there's nowhere
  to smuggle a hidden value.
- The Warden writes every output itself, from shown fields, and string-checks it.
- The trust page's attack suite plays a compromised Matchmaker and checks that every
  attempt is blocked.

The published files are listed in [attest.py](belong/attest.py) (`WARDEN_FILES`,
`MATCHMAKER_FILES`; the hybrid Matchmaker and its judge, `matching/hybrid.py` and `matchmaker_openai.py`
with the judge's fixed instructions, are among them). `test_the_warden_never_depends_on_the_matchmaker` makes sure no Warden
code comes from the Matchmaker, and `test_published_code_only_depends_on_published_code`
that nothing published relies on unpublished code.

### Testing Belong with your own agent

The trust page and its API (in [probe.py](belong/probe.py)) let anyone, or their agent,
test a sandbox that runs the same Warden and Matchmaker:

- **Canary test** (`POST /api/probe/canary`): plants unique secret words in hidden
  details (including a hidden open detail whose *name* is a secret) and private descriptions,
  runs a full week, then looks for them in what was sent out. A canary's own random words count
  anywhere, in every byte sent out, the shared list of details in use and the receipts included
  (nobody else can have them). Anything else a listing hides (an agent's own secrets, the name and
  values of a hidden open detail) counts where it could only have leaked: in what was sent about
  its owner to someone else (an introduction's view of them, read as audit A2 reads it; a reveal
  of their details; the phrase a question to anyone else quotes), as whole words, less what that person may see anyway (what the owner
  shows, and their own values said back in a reason). So a listing that hides a detail many
  others show isn't a false alarm. Canaries never consent to a reveal, so any hit is a leak.
  Agents can bring their own listings and secrets, open details included; an open detail that

### The independent audit

[leaks.py](belong/leaks.py) re-reads every output that was actually sent out, as
plain data, **without reusing the Warden's code**, so a bug in the Warden can't hide
itself. It watches every hidden value on the Marketboard and fails if any reaches
someone who shouldn't see it. It keeps its own copy of the reason's fixed sentences: when every
sentence of a reason is one of them, it reads the reason by character position, and a hidden value
in it is let go only if every character of it is fixed wording in every way the reason can be read
as those sentences (every sentence each part fits, every place each slot can end), or lies inside a
string the recipient may see. So a value cut across a slot or across the fixed words is still caught.
Any other reason is read whole, and the view's fields always in full.
In the demo the presenter panel runs it whenever anything it reads has changed, and it reads the last
Matchmaker run's proposals against the board as it was when they were made (`Marketboard.as_of`), so
someone hiding a detail that was a reason raises no false alarm before the next run, and a bad
proposal is still caught after the board has moved on. From the board's own record of changes it also
checks that every listing id keeps the owner it was first accepted under and is never accepted again
once its listing is deleted (R6), so an introduction and its reissues read only the listing it was
sent to.

With the Matchmaker AI on, it also reads every request its judge was sent (audit A8, #40), each against
the board as it was when the request was built (from the board's own record of changes): only the fixed
shape, each label a listing live then and never an id, each entry only what that listing showed and its
own description (with stretches taken out and nothing added), no first name or id of anyone, and a hidden
text of anyone only inside a text that listing showed itself, each found however its marks are written.
Every request the model's client recorded as sent must be one the Warden's check let through (#44) and,
while the Matchmaker still keeps every request, one it kept, so a Matchmaker that kept one request and sent
another would be caught. (The Warden checks each request before it goes; the audit is the independent check
after.)

It also rebuilds every shared list of details in use that was handed out (audit A7), with its own
code, from the board as it was when the list was built, and fails unless the list is exactly the
same: nothing below the crowd, nothing hidden or sensitive, nothing added, dropped or reordered, and
every text the shape of what it stands for, its words counted with its own code (runs of letters and
digits of the decomposed text whatever joins them, a capital after a lower-case letter starting a
word, and a run counted by its letters in a script written without spaces, or when it is longer than
an ordinary word).

## 5. What is NOT guaranteed yet (honest limits)

These need to be true before real people use Belong. They are deliberately visible
here so nobody mistakes the prototype for the finished service.

1. **No secure hardware, so "not even us" is not yet true.** Matching is a Python
   package whose isolation is enforced by tests, not by hardware, and it runs on a
   machine its operators control; with the Matchmaker AI on, its model runs on OpenAI's servers
   (limit 27). The strongest promise needs all of these (Step 3):
   - matching inside a hardware enclave (Nitro Enclaves / Confidential Space /
     confidential VMs), with no debug or operator access;
   - **hardware-signed** attestation (today's document is unsigned and says so);
   - listings encrypted on the person's device to the enclave's attested key, so our
     servers only ever relay ciphertext;
   - decryption and audit keys released only to attested code;
   - reproducible builds, so anyone can rebuild the Warden and get the same measurement;
   - an independent audit of the Warden's rules.
   The trust page's roadmap table tracks each of these.
2. **The string check catches exact values, not paraphrases.** If a reason said
   "you're both spiritual" instead of "Buddhist", the string check wouldn't catch it.
   This can't happen today because the Warden writes reasons from fixed templates. If
   an LLM ever writes reason text, it needs an additional semantic check, and
   templates should remain the default.
3. **Inference from who you're matched with.** Hidden fields can raise a score, which
   can change *which* of several qualifying people you're introduced to. The crowd
   rule (20 other people, counted in people) limits what this reveals, but doesn't make it
   zero. The value of *k* is an open question (SPEC §10); 20 is a placeholder.
4. **The intent text itself is read during matching.** It is never sent to anyone
   (introductions don't include it) and never part of a reason, but matching reads it: to tell
   dating from the rest; for who and what ages a dating listing wants, and how a listing meets,
   when its shown details don't say (a hidden one counts as not said); and as text similarity,
   which is part of the score a pair needs to qualify and orders each shortlist. So what someone
   types there can change whom they're matched with, and a person could type something sensitive
   into it. The personal agent spots common sensitive words (the published list in
   [schema.py](belong/schema.py): religion, politics, health, income, intimacy, sexual
   orientation and gender identity), records the ones that have a hidden category as that
   hidden detail and warns the person; that list can't catch everything. The Warden uses
   the same list on open details, so an open detail with a listed sensitive word is
   refused, but other wordings can get through, and a shown built-in written in free text
   (the "looking for" / "you are" phrases, a headline, topics) is checked against it only by
   the agents, not by the Warden. It matters most for the model agent: what it writes into
   shown details is checked only against that list (and reviewed by the person before
   saving). The rule-based agent doesn't rely on the list for that: it writes only words
   other people already show into anything shown (#3).
5. **Match-quality numbers are optimistic.** The synthetic people's listings are written
   from their own ground truth, as phrases and open details an agent would write, by code
   written alongside the grading, so 100% precision proves the pipeline works, not that
   agents understand language. Synthetic listings record what their agent understood
   (#33), as a model-powered agent's listings do, so the batch run mostly tests matching on
   those details; the keyword reader is only the fallback for what a listing doesn't record.
   The batch run's second pass, where a quarter of the agents write one detail differently,
   shows what inconsistent agents cost (limit 22). How well a model-powered agent
   understands people, and how consistently it names details, is tested only with scripted
   stand-ins, never a live model. That it asks when the kind of match is unclear is an
   instruction in its prompt, not something the code checks: a model can still save a guess.
   The rule-based agent asks only when its own keyword readers notice a second reading, so
   wording they don't know can still be misread. The real test is real phrasings it has
   never seen.
6. **Receipt key management** is a placeholder: the HMAC key is derived from the run
   seed. In production it belongs to independent auditors.
7. **Rate and approach limits** are simple in-memory counters, reset when the server restarts. 15 a day is
   the user's choice for the prototype; whether it should differ by kind of listing (dating vs selling) is open.
8. **The Warden's rules haven't been audited by an outside party** (planned for Step 3).
9. **The Warden checks that reasons are private, not always that they're true.** Where people
   are, how they meet and the open details they have in common are worded from both people's
   shown values (the distance between their cities; the open details the Warden itself works out
   they share), so those parts of a reason stay true even if a compromised Matchmaker cites them
   (#13). The phrase reasons ("They're a ska band") quote what the other person shows; whether
   that is what the reader asked for rests on the Matchmaker's yes/no flags, which the Warden
   doesn't work out again, so a compromised Matchmaker could introduce two people who don't fit,
   though nothing would leak. The city distances are approximate (city centres, a short fixed
   list, each known only in its own country). A distance is used only when both people show the same
   country, so any other city, or a city shown without a country, is only ever "near" a city of the
   same name.
10. **Receipts were extended beyond SPEC §7** (which lists `{check, result, timestamp,
    hash}`) with `seq` and `commitment`, to make the log publicly verifiable. Neither
    field contains content.
11. **The sandbox is not the live service.** Probes test a fresh copy built from the
    same code. In production, attestation must show the sandbox and the live service run
    the same measured image.
12. **The demo's personal agent uses a hosted model.** A person's chat with their own
    agent goes to the OpenAI or Claude API. That's the person's agent, not matching, and nothing
    the agent writes skips the person's review or the Warden. Real people need a
    decision here: an agent of their choice that Belong has certified, or one that Belong runs under
    its own privacy terms.
13. **Messages are held by the demo server in memory.** Matching never reads them, but the
    service could. Before real people use it, messages need end-to-end encryption between the
    two phones, so only the two of them can read them.
14. **A close match or an "also offer" question tells someone a little.** A close match shows the
    recipient the other person's shown details before that person has chosen them, which is why
    it needs the other person's criteria to be fully met and is one-way. An "also offer" question
    tells someone that a person somewhere is looking for a thing, without who or where; it only
    quotes a phrase that person chose to show.
15. **A deleted listing is kept aside in this prototype.** It's off the board and never matched,
    and its id is never accepted again, but a copy stays so the independent audit can still check
    what was already sent, and so the Warden can reissue, reduced, an introduction with it when the
    other person changes their listing (#12): what is kept of that introduction is the latest
    reissue, checked against the deleted listing as it was when deleted, and the deleted listing's
    view keeps only what it already had and the other still shows unchanged. A real service needs a deletion policy: what is erased,
    when, and what an auditor may keep.
16. **Through the connector, messages pass through the person's AI assistant.** When someone uses
    Belong inside their own assistant, their conversations with matches are shown there, so the
    assistant's provider handles both sides' messages. The match is told, but can't opt out of
    it in this prototype. A per-person choice is a possible next step.
17. **The hosted demo is still a demo.** Run online (README, "Run it online"), it is one shared
    demo session for everyone who has its password: anyone using it at the same time sees the same
    two phones, and what they type stays in the server's memory until it restarts. It runs on Google
    Cloud, so Google, and anyone who can manage that project, could in principle read that memory.
    The password keeps strangers out (and off the AI key): it's asked for on its own sign-in page and
    sent over HTTPS; the browser then keeps a cookie that proves it without containing it (30 days, or
    until the password changes), guessing pauses after 20 wrong tries a minute, and the hosted demo
    refuses to start without a password (`_authorized`, `_login` in [server.py](belong/server.py);
    `tests/test_server.py`). On a VM the demo still listens only on the VM itself, behind Caddy;
    run locally, only on your own machine. Use made-up details only.
18. **What you write to a simulated person goes to the AI provider** (OpenAI or Anthropic), because a
    model writes their replies. Only in the demo, and only to synthetic people: messages between two real
    people are never sent to a model.
19. **Taking over is a presenter's tool.** The inspector shows every synthetic person's hidden details,
    and taking one over lets whoever runs the demo act as them and see their hidden details on their
    phone. A real service would never let anyone act as someone else; it's there only because these
    people are synthetic. Their phone is still held to promise 23, so nothing about them reaches
    anyone else except through the Warden.
20. **Who you'd like to meet is shown to your matches by default** (#33), like your gender. A match
    already implies most of it (you're only introduced to people you'd like to meet who'd like to
    meet you), but not all: someone open to anyone shows that to a match who only asked for one
    gender. You can hide it; matching then reads your description instead, so hiding it costs
    nothing as long as your description says who you'd like to meet. Whether it should start hidden
    for people open to more than one gender is open.
21. **The shared list starts empty.** A name, scale or value is listed only once 20 different
    people show it on listings unchanged for a week (#38). Until then, agents writing details on
    the spot agree only when they happen to choose the same name, steps and words, and a required
    wish with nothing comparable on the other side means no match, so early on, and for anything
    rare, people get fewer matches than they could. The model agent is told to reuse what's listed
    (an instruction; only "one name, one meaning" is checked). The offline agent writes nothing the
    list doesn't have, so with an empty list it writes no phrase or open detail and asks instead.
    The demo and the batch run date their synthetic listings 8 to 90 days back, so their list is
    filled from the start; a real service would start with nothing on it.
22. **A detail named or scaled differently costs matches.** Two agents can call the same thing by
    different names ("skill", "ability") or write different scales. A wish is compared only with a
    detail of the same name, and steps by their words (by distance only on the identical scale), so
    that pair isn't matched on it: a detail that can't be compared never makes a wrong match while
    the wish is required, but it costs some. A wish kept as "ideally" because the person's own words
    don't say it (#45) waives a detail that can't be compared (a listing at exactness 0.8 or more with
    one is made less exact), so there it can: that is the cost of a must the person meant but never
    said (limit 28). In the batch
    run's dialect pass (a quarter of the agents write one detail differently), where every synthetic
    person says each must they have (with its value, or as a yes when their agent asks), precision
    stays 1.0 while coverage falls from between 0.86 and 0.94 to between 0.81 and 0.89 (seeds 1 to 4
    and 7). Read by values alone, without their yes, in the pass where nobody types their musts with
    their values, precision would fall to between 0.98 and 0.992 at seeds 1 to 4, 6 and 7; their
    descriptions still say most of their musts, so that is the cost on the rest only (27 of 123 at
    seed 7, #45)
    (`test_a_detail_written_differently_never_makes_a_wrong_match`,
    `test_saved_listings_never_make_a_wrong_match_and_values_alone_would`,
    `test_the_batch_run_stays_precise_and_leaks_nothing_with_dialects` in
    [test_synth.py](tests/test_synth.py)). Whether a name says what a detail measures, and whom
    it is about, is the agent's judgement; no fixed rule can check meaning.
23. **A few general word lists remain.** No list of activities, detail names or values is in the
    product, but some code still reads fixed lists of general English words: in
    [matcher.py](belong/matching/matcher.py), role words (`ROLE_WORDS`: teach, student, partner),
    words that mean the same role (`_SYNONYMS`: mentor, coach, instructor, tutor and guide as
    teach; learn, beginner, apprentice, pupil and novice as student; buddy, friend, companion and
    pal as partner), purely social words (`SOCIAL_WORDS`), which roles a wide net lets stand in for
    each other (`_ROLE_RELAX`), umbrella words that never count as shared (`_UMBRELLA`) and phrase
    stop words (`_PHRASE_STOP`), and which roles are the one served (`looking_for`: student,
    customer, client...); the rules in [intent.py](belong/matching/intent.py) that tell dating from
    the rest and read ages, which read how a sentence is built plus a few general words for romance
    and time together (`_ROMANTIC`, `_TOGETHER`, `_OCCASIONS`) and the grammar words that may follow a
    decade said as an age (`_DECADE_END`: who, that, and, in, with...) and the few words that hedge a
    preference before one (`_HEDGE`: ideally, preferably, probably...), and the grammar words after
    "dating" that keep it a verb (`_GRAMMAR_WORD`), never a trade, service, hobby or genre; in the
    offline agent ([agent.py](belong/agent.py)) the forms of partner and teaching
    phrases (`_PARTNER_PHRASE`, `_TEACH`, `_LEARN`), of what someone says about themselves (`_MINE`),
    with the adverbs and degree words that may stand between "I'm" and what they are (`_PREDICATE`:
    usually, really, a total, kind of...) and the negation family that denies it (`_NEGATION`: not,
    hardly, far from, neither, nor, except, doubt...), and of where someone is; and the role words used to word which side a listing is on (`CLIENT_WORDS` in
    [demo.html](belong/web/demo.html), `_CLIENT_WORDS` in [demo.py](belong/demo.py)). They are
    roles and sentence structures, not activities, but they are English only, and wording they
    don't know is missed: that costs a match or a question, never privacy. A role noun they don't
    know (a "player", or a partner or companion in another language) never makes a match on its
    own: two phrases with the same main noun are compared on their other words, in any script
    (`_about` in [matcher.py](belong/matching/matcher.py); `SameHead` in
    [test_matching.py](tests/test_matching.py)). At the default exactness and above, more than half
    of those words must be in common, and two phrases that each have a content word the other lacks
    never meet, however many they share: so one or more describing words in common never meet when
    another differs, in any script and whatever the word order, a role noun first ("amico di ...")
    or last (the main noun is read as a phrase's last word unless it is a known role word, so in a
    language that puts the role noun first it is the "rest" that is compared, and both differing
    still never meets). A wide net (exactness under 0.5) asks for only half of them (in the other's phrase or in
    what they show about themselves), so there two phrases that share one describing word out of
    two, such as "an evening sketching partner" and "an evening baking partner", can still be
    introduced, and so can a close match judged that way for someone who opted in to close matches.
    The Warden's identifiers rule also reads a few English words for looks, marks, workplaces, homes,
    meeting someone and people, besides grammar words (limit 26), and its full-name rule the lower-case grammar
    words that stand inside a name in many languages (`_NAME_JOIN`: de, da, dos, van, von, der, bin, ibn, al, la...):
    a clue or a name it misses is left to the model agent's judgement, and one it misreads refuses a listing, never
    leaks anything. "Dating" before a person with describing words first ("dating older men") or a word made from a
    verb ("dating widowed ...") reads as dating; a verb straight after a sentence's first "Dating" ("Dating feels
    ...") or another adverb ("dating long-term") is read as a noun it describes and set aside, which costs a
    question.
    [test_neutral.py](tests/test_neutral.py) guards the rest: it reads every string in product code
    and pages (f-strings included) and fails on a word of the synthetic people's stories or two words
    of one of their vocabularies written out together, with one list exempted by name
    (`_UMBRELLA`, which holds "beginner" and "advanced"; the full-name rule's typed list of the demo's
    cities and languages is gone, limit 26).
24. **The shared list is public, and 20 is a placeholder.** Everything on it is shown by at least
    20 different verified people, so it points to no one; but 20 accounts acting together could
    still put a word on it, and the value of *k* is open (SPEC §10). Every agent reads it, so its
    shape rule (a phrase at most 6 words, anything else at most 5, no sentence punctuation; words
    counted as runs of letters and digits of the text decomposed for compatibility whatever joins them (a
    circled, squared or full-width letter is its letter, and a letter written as a symbol with no
    decomposition, such as a negatively squared one, counts as a letter), a capital after
    a lower-case letter starting a word, in a script written without spaces one word for every 3
    letters, and in any other script a run longer than 12 letters one word for every 5) keeps long
    instructions off it, whether spaced, joined by other characters or run together into one word,
    and agents are given it as data after a fixed line. But no word count can tell an instruction from
    a phrase: a short instruction of 6 words or fewer, however they are joined (in a script written
    without spaces, up to 18 letters; run together, up to 30), and a longer one cut into up to 6 runs
    of up to 12 letters each, wherever the cuts fall ("copytheirhid denhomestree ..."; 60 characters
    at most), that 20 people show for a week could still be listed, so an agent must never take an
    entry as an instruction. The week's wait reads each
    listing's last-changed time as the person's agent sent it, so a modified agent could backdate
    its own listing and skip the wait for its own contribution; it would still need 20 different
    verified people.
25. **The offline agent reads only a few first-person forms.** It writes a listed value as yours
    only when you say it about yourself: as something you are ("I'm a…", "I am…", with only an article
    and adverbs or degree words in between, or the words of the detail's own name, as in "I'm free
    on…"), as what you like or do ("I like / enjoy / love / play / go / do…", "I'm into…"), or "my …
    is…", and a list of one detail's values after those ("I'm free weekends and weekday evenings"), unless
    another clause starts with a value (a verb of being or seeming, a modal, the negation family or a request after
    it: in "I'm a thrower, a glazer would suit me" only "thrower" is written).
    Never from a wish, a description of someone else ("someone who's into opera", or a value followed
    by a possessive: "a seasoned crew's coach", never a contraction such as "it's" or "she's"), the object of something you do ("I'm leading a weekend
    group", "I love hosting newcomers"), or where the negation family reaches it in the same phrase
    ("not", "hardly", "far from", "neither … nor", "no longer", "anything but", "except", "doubt"),
    including a clause that depends on a denied verb ("I don't think I'm…"; only "…, and I'm" or "but
    I'm" starts afresh), and nothing when you name two steps of one scale. A denial said in words
    outside that family can be missed, and the person checks every value before anything is shown. Said any other way (a value
    after a comma that doesn't continue a list, "I'm good at…", "I'm almost…", or "a woman who loves
    hiking" about yourself), it isn't written, so you may need to add it yourself or say it again; it never guesses. Words the
    rule doesn't know as adverbs ("I'm hopefully…") stop it rather than let a value through. It never
    writes a wish about the other person, and these forms are English only.
26. **Known gaps, not fixed yet:**
    - the full-name rule is a floor, a pattern over capital letters (`full_name_pairs` in
      [warden.py](belong/warden.py)), and it reads no meaning. One word that is never part of a name is enough to
      clear a pair. So it lets through a name written in lower case; all in capitals ("ANA LIMA") or with one word
      in capitals ("Marie DUPONT", "ILSE Varga": the rule that a word in capitals is never part of a name is meant for
      abbreviations such as "BMW" or "NYC"); with one word that is a month or a weekday ("June Okafor", "August
      Lindqvist"); with one word that is a whole one-word place on the shared list, or the listing's own one-word
      city or country ("Jordan Okafor" once a place in Jordan is listed, "Victoria Novak" from someone in Victoria;
      one word of a place with more words unlocks nothing on its own); as one word; joined by punctuation; at the
      start of a sentence (after a full stop, a question or exclamation mark, a colon or semicolon, a dash, an opening
      bracket or a straight quotation mark, but not after an initial's or a short vowelless title's full stop); in a
      script without capital letters (Arabic, Chinese, Devanagari...); a first name or nickname alone; and a name
      whose words are the listing's own shown city or country (a person could enter one as their city: it is then
      shown to every match, and in person they only meet a city of the same name, limit 9). Catching those is the
      person's own model agent's judgement (`singles_out`), which needs a live model and is untested against one;
      the rule-based agent has only the floor. The other way, it refuses two capitalised words that are a place, a
      language, a title or a brand ("Old Norse", "Doctor Who", "Raspberry Pi", and place names with a lower-case
      particle, "Rio de Janeiro") unless a word is part of the listing's own shown place or a listed place written
      out whole, in capitals, a month or a weekday: there is no built-in language field, so a language never
      unlocks. It also refuses an initial that ends a sentence before a capitalised word ("I'm in group B. Anyone
      ..."), and a list typed one item per line where one line ends and the next starts with a capitalised word (a
      line break is read like a space, so that it can't hide a name; the person and the model are told to end the
      line with a comma or a full stop). A model agent rewords such a pair before saving; with the rule-based agent,
      or on the phone, the person rewords it themselves. Months and weekdays are English (the standard library's
      names in the locale Python starts in), and a place written out whole unlocks the capitalised word next to it
      too ("the Port Louis Market"). A live listing keeps the listed places it was accepted with until it is
      withdrawn, so a place a later list drops still unlocks that listing's own description (never anyone else's);
    - the identifiers rule (`identifier_problems` in [warden.py](belong/warden.py)) is a floor too: it reads
      how an English sentence is built, with a few words. Its traits are the looks words of the rule it
      replaced (`_LOOKS`: tall, short; `_LOOKS_NOUNS`: hair, glasses, beard, freckles; a nose ring) and the marks
      (`_MARKS`: scar, birthmark, tattoo, piercing). Its anchors are that rule's workplace words (`_WORKPLACE`:
      work at, works at, working at, and four jobs, barista, cashier, employee and bartender, "at"), "lives at / on"
      (`_HOME`), five verbs for seeing or meeting someone (`_ENCOUNTER`: saw, seen, met, noticed, spotted) with the
      poster or no one as their subject, "the" + a clock time, and "the", "that" or "this" + a word for one person at
      a place (`_PERSON`, `_ONE_PERSON`: matching's person words with the words it reads as "partner"); the rest is
      grammar (`_GRAMMAR`, `_DEGREE`, `_ON`, `_FEATURE`, ...). What the poster says about themselves (what they offer,
      an open detail about them) is read as if it began "I'm ..." (or "my" before a detail's name). So it misses
      other looks ("blonde", "a shaved head", a moustache, a height in numbers), other roles ("the receptionist at
      the clinic"), other ways to say where someone is found ("who sits by the window", someone another person saw:
      "my friend saw her at ...", or "a man at my gym": an indefinite person at one's own place is built like
      "someone at my level" or "on my own", so it isn't read as an anchor), a mark's place said without whose body
      it is ("on the back of the neck"), a look said of a role with no anchor before it in the sentence, someone
      else's look written after "my" ("my short barista"), and any other language. It over-refuses three looks in
      one listing even when they're preferences ("a tall man with a beard and glasses", as the owner chose) and a
      group that shares a mark ("anyone else with a tattoo of a cat?"). And it counts as a clue what isn't one, so a
      listing with one other clue (a look, or a place to find them) is refused: "works at the weekend" ("the" reads
      as a place), the clock time of the poster's own plan ("a partner for the 19:30 class, ideally tall"), how the
      poster met someone else ("we met at a pottery class" with one look), a looks word for a thing it doesn't
      recognise as one ("Short, flat routes" opening a sentence; a wish about the other person such as "walk
      length: short"; a looks noun after "with" or opening a phrase before a word that makes it a thing, "a partner
      with hair salon experience"; a "both" wish named with a looks word or a mark, "tattoos: traditional"), and the
      poster's own looks or job said in a way it doesn't recognise as theirs (in a detail about them, "the tall
      barista at the café" reads as someone else, since a describing word stands before the job). The person's own model agent is told the rule and judges meaning (its
      instructions, untested against a live model); the rule-based agent has only the rule;
    - the vouching rule refuses only "verified" and "KYC" as whole words, so other claims ("official
      partner", "approved") can still be written into a shown value;
    - invisible filler characters that count as letters (such as the Hangul fillers) can carry a word
      past the sensitive-word and vouching checks, and the specific-person rules (they drop characters that show
      nothing only when Unicode marks them as format characters or variation selectors); only someone deliberately
      misdescribing themselves, or hiding a search, would write one;
    - travel distances are known only for the cities in `CITY_COORDS` ([schema.py](belong/schema.py));
      any other city only meets a city of the same name (limit 9);
    - the Warden doesn't check shown built-ins written in free text (the phrases, a headline,
      topics) for sensitive words (limit 4);
    - a hidden value that the same person also writes into their own shown headline isn't caught;
    - when your agent brings a part in line with a change you made (#34), the fixed rule lets it use only words that part
      had and your new wording, so a fact in a new word can't be added; it can still reorder those words, add a word
      of two letters or fewer ("no", say), and take a word that starts like an allowed one, at most three letters longer,
      as the same word ("card" for "car"). A part that says a word you replaced only in another form (a plural) isn't
      counted as saying it. Topics written again may still name a hidden value in other words (another name for it, or
      the words of one spread over two topics), and a new word that is a form of a hidden one is refused even where it
      means something else. You review the draft before it goes live;
    - how consistently real models name and scale details is untested (it needs a live model).
27. **The Matchmaker AI is a mock, run by OpenAI.** Until the Matchmaker's model runs enclosed (Step 3),
    OpenAI's API stands in for it, so it is for synthetic and test profiles only, never real people:
    - what it is sent goes to OpenAI and is processed under OpenAI's API terms. That is a contract, not
      the design: "not even we can access it" still needs the model enclosed with the Matchmaker (a
      self-hosted open-weights model inside confidential computing, reached by changing
      `BELONG_MATCHMAKER_URL` only);
    - descriptions are sent to it (with every first name, id and hidden text taken out), although they
      are never shown to people. Like the string checks (limit 2), taking out hidden texts catches exact
      values (however their quote marks, dashes and invisible characters are written), not paraphrases:
      a description that says something private in other words still says it to the AI;
    - a hostile Matchmaker could still say a little to the AI through what the checks can't read as
      text: which listings it puts in a request, in which order, or which stretches it takes out. Only
      running the Matchmaker and its model enclosed together closes that;
    - the client that carries requests to the model ([matchmaker_openai.py](belong/matchmaker_openai.py))
      is Matchmaker code, in the same process. The Warden checks every request before it is handed to
      it (#44), so modified matching code can't get a hidden detail past the Warden, but a modified client
      could send something else, and its record of what went out is its own word. It is published and
      measured; only running the model enclosed with the Matchmaker takes it out of the picture. The
      client runs the Warden's check again before each of its own retries and each next response
      format (`OpenAIJudge(recheck=...)`, `_JudgeOffLock._ask`), so a request someone has since hidden,
      paused or deleted a listing of is never sent again (`test_a_retry_or_another_format_goes_only_if_still_permitted`);
      what an earlier attempt already sent can't be recalled;
    - the model is told never to follow a listing's instructions, but that is an instruction to a model,
      not a guarantee. A listing that tells it to propose it to everyone can, with a model that obeys, be
      introduced to people it doesn't suit: the hard rules (#39) and the limit of 15 introductions a day
      (#17) bound that spam, they don't remove it. One listing's text can also sway the verdicts on the
      other pairs of a request it is in (while it is there: #41);
    - how well the AI judges meaning, and whether it spots a listing hunting one person, are instructions
      to a model, tested here only with stand-in judges. It is asked about the listings a run matches (in
      the demo, the phones' own), at most as many in a run as the pairs it may judge. `tools/compare_judges.py` measures it against the
      rules and the simulation's ground truth, but it needs the owner's key and go-ahead (it costs money),
      so it is never run in the tests;
    - it costs tokens: at most 80 pairs a run go to it (40 to a request), and at most 80 listings are asked
      about alone; verdicts are kept until a listing of their request changes, and the rest are decided by
      the rules. In the demo its answers arrive a few seconds
      later, so a pair may wait for a run or two.
28. **A must comes from your words by a word rule, not by what they mean (#45).** The rule reads only
    whether words are yours, and when you typed them, never what they say:
    - your answer to your agent's question counts by when you typed it, not by what it says: the words
      your agent quotes from the message you typed next, after the latest save that kept a wish as
      "ideally" and told your agent to ask about it, count as your answer, so an agent that stays over-eager and quotes your "no", or words
      of that message about something else, keeps its must. A quote from anything you typed before that
      save, or from a message after your answer, never counts. In the batch run, where the agents
      that made a must up quote the person's no, the rule wins back nothing (coverage 0.793, as without
      it). Only your own control on your phone can stop that (not built yet);
    - any one value counts: more values widen who meets a wish, never whom it shuts out for not showing
      the detail, so an agent that writes one of your words (about anything) as an extra value of a must
      it made up keeps that must. So does a value you typed about yourself ("I'm free on Saturdays", "I
      speak Dutch") or in a denial ("they don't need a car") (in the batch run, 4 of the 53 made-up
      musts stay one this way);
    - a must you said in other words than any value your agent writes is only "ideally" until you
      answer its question, one more message (asked once: if your answer doesn't come next, it stays
      "ideally" until you say a value yourself), and a must you meant but never said is only "ideally"
      until you say it; meanwhile, where the other person doesn't show that detail, you may be introduced to someone it
      doesn't suit. An "ideally" wish still fails anyone who shows a value that doesn't meet it;
    - exactness is your agent's reading of how exact you want your listing (you can also set it on your
      profile, and then the wishes your draft already had count as musts for it). A save at 0.8 or more
      with a wish that passes none of the rules is made less exact (0.7) until you answer: then every
      "ideally" wish on it waives a detail that isn't shown or can't be compared, an own "any" meets its
      wishes, and it needs a slightly lower score, so a must you meant but said in other words can let
      through someone it doesn't suit (read by values alone, the batch run's precision would fall to
      0.98 at seed 7, counting only the 27 of its 123 musts that the people's descriptions don't say:
      with more musts said only in other words, it would let through more);
    - a separate listing your agent starts counts the message that led to your other listing's last
      save, so a must you typed there for the other listing counts for the new one too;
    - a word in another form is read by one length rule in every language (in Hangul with its
      particles, in a script without spaces anywhere inside a run), so an unusual form of a word you
      did type can be missed (in Hangul a syllable of two letters, with no final consonant, counts only
      standing alone, not with a particle on it), and a short word inside a longer one can count (in a
      script without spaces, and in Hangul a word of three letters or more at the start of a longer one,
      a one-syllable word with a final consonant among them); a number and the word right after it are
      one word, so a number written with another word for its unit than the agent's ("10 kilometres"
      for "10km", or "10 kms": a unit of one or two letters counts only as itself) is missed, a
      one- or two-letter word between two numbers is read as connecting them even where it is a unit
      ("5 km 3 times" is said without "km"), and a decimal or a time written with another separator
      than the agent's is the same number ("9.15" for "9:15"), while numbers listed with commas and no
      spaces are read as one ("levels 1,2,3" doesn't say "level 2"), and a one- or two-letter word after a
      number and before another word is read with the number ("level 4 or above" isn't said by "level 4+
      or above"): each costs one more question, never a must you didn't say;
    - a phone window that missed your agent's saves and sends Save draft without the copy it changed can
      put back an exactness your agent's save had lowered, and the next save then keeps it as it was;
    - your phone shows a wish about the other person that isn't a must as "Ideally, I'd like..." on
      your profile, and a match sees "(ideally)" next to it; a wish about what you both share reads the
      same either way (`OnThePhone` in [test_said_wishes.py](tests/test_said_wishes.py)). There is no
      control yet to make a wish a must or not, and values you type on your profile don't count as your
      words yet.

## 6. Glossary

- **Intent:** what the person is looking for, in their own words.
- **Listing:** the person's details, each marked *shown* (others may see it) or *hidden*
  (used only for matching, never shown).
- **Exactness:** 1 = exactly what I said; 0 = cast a wide net.
- **Proposal:** the Matchmaker's internal suggestion. It is never sent to anyone as-is.
- **Matchmaker AI:** the model that judges the fuzzy part of matching inside the rules (the hybrid
  Matchmaker). In this version a mock: OpenAI's API standing in for the model that will run enclosed,
  for synthetic and test profiles only.
- **Judge:** what the hybrid Matchmaker asks about each pair (the Matchmaker AI, or a stand-in in
  tests): plain data in, verdicts out.
- **Introduction:** the only output about a match: shown fields plus a reason.
- **Built-in field:** one of a fixed set of details every listing may have (where and how to
  meet, the phrases, dating's rules, and the hidden categories), with fixed rules of its own.
- **Open detail:** a detail the person's agent names on the spot: about the person (me), what
  they'd like the other person's own value to be (them, a *wish*) or the request itself (both),
  compared as the same value or on a scale of steps the agent writes out.
- **Reason field:** something both people show that connects them: a built-in field (the same
  city, how they meet) or an open detail they have in common, which the Warden works out itself.
- **k (crowd threshold):** a hidden value counts only if at least k other people share it, counted
  in people, not listings.
- **Shared list (details in use):** the open details, scales, values, phrases and places at least
  k different people show, built by the Warden once a day and given to every person's agent.
- **Receipt:** proof that a check ran and passed or failed, with no content.
